# shell 长脚本先落文件再运行

`shell` 的 `argv` 是字符串数组，工具描述与被拒时的提示已经给出正确形状。这条记的是它**什么时候**会写错，以及写错之后往哪走。

失败几乎不发生在短命令上，而是在脚本一长、引号和换行一多的时候：整次调用被序列化成一整个字符串，或者脚本正文被塞进一个超长元素。刚启动的子代理最容易踩——它没有你这一路的纠错记录，第一次调用就照着「敲一行命令」的习惯写。

## 做法

- 超过一行的 Python 或 shell，一律先 `write_file` 写成工作区里的脚本，再用数组运行它。这不是被拒之后的补救，而是默认写法：脚本可复跑、可 diff、可交给子代理，也不用为引号和换行做任何转义。
- `write_file` 的返回里带着它实际接受的路径，直接拿这个字符串去拼 `shell` 调用，不要凭记忆重写一遍（两套路径写法的差别见 `workspace-path-rules`）。
- 结果里出现关于 `argv` 被规范化的说明，意思是这次调用本来就不是正确形状：下一次直接改成落文件的写法，不要在原地把字符串拼得更长。
- `sleep` 与等待类包装在执行前就被拒，没有后台、没有轮询：需要长时间的工作切成能在单次超时内跑完的块，中间结果写文件接力。
- 输出有内联上限，超出会截断并落盘。让脚本只打印结论性的少量行，完整结果写进工作区文件后按需读回。

## 写进 task 的一行约定

给任何能用 `shell` 的子代理，在 task 正文里原样带上这一行：

> `shell` 的 `argv` 是字符串数组（如 `["python", "notes/probe.py"]`）；超过一行的脚本先 `write_file` 再按路径运行，不要把脚本正文当参数传。

## 教训

argv 形状类错误是多个实验里最高频的一类工具失败，并且集中在新启动的子代理身上：条目已挂载、父会话每折都确认过、task 里也写了这行约定，它仍然逐折复现，且大多数犯错的子代理从未打开过这个条目。所以两件事都要做——约定写进每一份 task，第一次被拒后立刻切到落文件的写法，而不是再试一次更长的字符串。
