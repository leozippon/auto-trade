# shell 长脚本先落文件再运行

`shell` 真正执行的是一个 argv 数组，中间没有 shell。数组是标准写法；整行命令字符串会被按 POSIX 词法切分成数组，把整个数组 JSON 编码成一个字符串（哪怕 `python -c` 正文里的换行没有转义）会被按元素还原，只含一个整行命令的单元素数组会被拆开，命令写在 `cmd`/`command` 里也会被移到 `argv`，结果里的 `argv_normalized` 会说明这次改写。所以调用形状本身已经不是失败点，剩下两处仍然会被拒：

- 命令行里带管道、重定向这类 shell 符号——没有 shell 会解释它们，必须显式写成 `["bash", "-lc", "<整行命令>"]`。
- 单个元素超过 `shell` 工具说明给出的字符上限（同一个数字也写在 `argv` 元素的 `maxLength` 上，被拒时的报错也会带上它）——脚本正文被整段塞进一个参数时就会撞上它。

第二条几乎不发生在短命令上，而是在脚本一长、引号和换行一多的时候，刚启动的子代理最容易踩：它没有你这一路的纠错记录，第一次调用就照着「敲一行命令」的习惯写。

## 做法

- 超过一行的 Python 或 shell，一律先 `write_file` 写成工作区里的脚本，再用数组运行它。这不是被拒之后的补救，而是默认写法：脚本可复跑、可 diff、可交给子代理，也不用为引号和换行做任何转义。
- `write_file` 的返回里带着它实际接受的路径，直接拿这个字符串去拼 `shell` 调用，不要凭记忆重写一遍（两套路径写法的差别见 `workspace-path-rules`）。
- 需要管道、重定向或通配符时显式走 `["bash", "-lc", "..."]`，不要指望字符串形式替你解释这些符号。
- `sleep` 与等待类包装在执行前就被拒，没有后台、没有轮询：需要长时间的工作切成能在单次超时内跑完的块，中间结果写文件接力。
- 输出有内联上限，超出会截断并落盘。让脚本只打印结论性的少量行，完整结果写进工作区文件后按需读回。

## 写进 task 的一行约定

给任何能用 `shell` 的子代理，在 task 正文里原样带上这一行：

> `shell` 执行的是 argv 数组（如 `["python", "notes/probe.py"]`），中间没有 shell：管道和重定向要写成 `["bash", "-lc", "..."]`；超过一行的脚本先 `write_file` 再按路径运行，不要把脚本正文当参数传。

## 教训

argv 形状类错误曾是多个实验里最高频的一类工具失败，且集中在新启动的子代理身上：条目已挂载、父会话每折都确认过、task 里也写了约定，仍然逐折复现。结论不是再多写一遍约定，而是让工具吸收这类等价写法——现在数组、JSON 编码的数组字符串、整行字符串与 `cmd` 字段都能跑。留下来要靠自律的只有「长脚本先落文件」和「管道显式走 `bash -lc`」这两条。
