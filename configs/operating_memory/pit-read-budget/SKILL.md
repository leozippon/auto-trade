# 窗口化 PIT 读取

「决策期读取必须加窗」是运行合同里的硬规则。这条记的是它为什么还会被违反，以及怎么在花掉正式回放之前发现。

## 做法

- 先算出本次真正需要的最早日期，按日期过滤后再读，只列会用到的列。宽表的全列读取是超时的主要来源。
- 逐日重复的滚动窗口在决策内自己维护，不要每天重算整段历史。
- 按冷启动那一天估算耗时，不要按平均日：第一天往往要读满整个回看窗，也常常是唯一会超时的那天。
- `output/` 一旦可运行就先用 `smoke_backtest` 量一次单日耗时，确认离单日上限留有余量，再进入正式验证。
- 重的拟合放进 `fit`，它有独立且宽得多的预算；`generate_orders` 只读系数、算当日特征。

## 教训

一个折的全部正式回放都因为同一处无窗口读取而超时失败，没有留下任何可选节点——超时发生在回放里，不在冒烟里，所以直到正式预算烧完才暴露。同样的读法在后来的实验里再次出现，说明它不是偶发错误。
