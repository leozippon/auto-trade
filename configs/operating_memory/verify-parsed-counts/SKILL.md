# 解析前先核对真实输出

自己写的验收脚本一旦解析假设错了，会安静地给出一个看起来合理的错数。最典型的是数 diff：经典 `diff` 用 `<`/`>` 和 `NcN` 标记，按 `-`/`+` 开头去数改动行，真正改过的文件也会被数成 0。

## 做法

- 先跑一次原始命令、看几行真实输出，再写解析；不要凭印象假定格式。
- 数改动行：`diff -u` 配 `^[+-]` 并排除 `^[+-][+-]` 的文件头，或经典 `diff` 配 `^[<>]`。`diff -u | wc -l` 把文件头和 `@@` 也算进去，不是改动行数。
- 解析出的数字与另一处观察矛盾时（脚本说没改、读文件却看得见改动），先手工核一遍再下结论；解析脚本用来省事，不用来代替核对。

## 教训

一次提交前验收报出「零改动」，结论完全来自错误的解析假设，产物其实改过；同类的 `wc -l` 数法在别的会话里也出现过，都是没看真实输出就写了解析。
