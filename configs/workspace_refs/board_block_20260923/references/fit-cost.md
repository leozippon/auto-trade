# 学习型候选的 `fit` 成本纪律

自写笔记。本仓库在这条线上赔掉过最多的回放年——两次整期批次撞上 `fit` 上限，每次把整批的回放年一起赔掉。本臂是学习型的，所以这一页把要做的几件事写死。

## 三条上限

| 边界 | 值 | 性质 |
|---|---|---|
| 一次 `fit` 的墙钟 | 运行事实 `budgets.strategy_fit_timeout_seconds`（基准 **3,600 秒**） | `batch_validate` 的并发池按本批并发路数放大它（三路 = 三倍），**但只补偿本批自己引入的争用**；跨实验的争用不在补偿之内 |
| 一次复核决策的墙钟 | `budgets.strategy_inference_timeout_seconds`（基准 **360 秒**） | 超时与抛错一样，整个回放失败 |
| 策略容器 | **8 核 / 16 GiB**，`/tmp` 与 `/dev/shm` 各 2 GiB（都算在这 16 GiB 里） | **`--memory-swap` 与 `--memory` 同值：超了不是变慢，是直接 OOM 杀掉（退出码 137）**。会话容器是同一个边界，所以在 `shell` 里量到的峰值就是正式回放的口径 |
| 显存 | 本臂 `gpu_count = 0`，不分配显卡 | 载体是 CPU LightGBM，本块是 numpy 与 pandas 的日频聚合；**没有任何一步需要 CUDA** |

墙钟为什么会被撞上：同一份代码在轻载与重载下的差别不是百分之几。同族起步包的冒烟里，同一个槽、同样的天数、同一份代码在两个时刻读到 **255.5 秒**与 **193.9 秒**，同一批里的另一条腿读到 **300.5 秒**。

## 本包起步包量到的那条线

实测读数、口径与限制写在 `sources.md`，这里只写怎么用它们：

1. **按真实宿主回放那一组数做预算，不要按容器探针那一组。** 探针不走 Broker、不走执行器、不与别的负载抢主机，它证明的是「能跑通」，不是「一定来得及」。
2. **第一研究年的读数不算数。** 那时训练窗口有一半落在数据下限之外，样本少、`fit` 快、内存低，外推会骗人。
3. **真正会把成本顶上去的三件事**：`REFIT_PERIOD` 从季度改月度（一个研究年 4 次重训变 12 次）；`knobs.TRAIN_YEARS` 加一年（面板、特征与训练行数同比例涨）；块的列数翻倍（面板内存与每次分裂的候选列同比例涨）。**每改一件，重量一次。**

## 本包要求的三件事

1. **整期批次之前，先在研究期靠后的槽上用 `smoke_backtest(start=...)` 跑一次**，读 `resources` 里的 `fit_seconds` 与 `peak_memory_bytes`，写进结果笔记，并确认峰值离 16 GiB 有明确余量。
2. **同一个 `start` 复用。** `window_build_seconds` 几乎全是那个窗口一次性的开窗成本（主机侧），**付一次，后面同一个 `start` 的探针直接复用，永远不要乘以天数**；整期批次从研究期开头开窗，根本不付这一笔。
3. **拟合的候选要报种子差。** 这个家族的方向研究在三个种子之间散开过 4 pp/年 的 alpha，比通常要争的那点信息比率还大。提名之前必须有两个种子的主动信息比率之差；**比种子差还小的优势不是证据**。

## 三条实现纪律

- **线程数写死在 8 以内**（`knobs.PARAMS["num_threads"]` 就是这么钉的），不是留给库去猜 CPU 数。容器就是 8 核，多路并发时让每一路自己抢满会互相拖垮。
- **训练面板与事件读取都按成分并集下推 `ts_code`**。不下推就是把全市场三百多万行读进 16 GiB 的容器里，这是本族最容易犯的一次 OOM；事件域的表是全市场的，这一条在本臂比在别的臂更要紧。
- **不设退路打分器。** `fit` 样本不足、读不到状态、选中的数据集在窗口里没有任何可见行，都直接报错。回放失败好过悄悄交易另一套策略，更好过悄悄用一块全空的特征。
