# `fit` 与决策的成本

自写笔记。本臂四条腿里两条根本不训练，所以这一页比同谱系的包短；它写清楚哪条腿花什么、边界在哪里、第 0 轮要量什么。全部实测读数在 `sources.md`。

## 三条上限

| 边界 | 值 | 性质 |
|---|---|---|
| 一次 `fit` 的墙钟 | 运行事实 `budgets.strategy_fit_timeout_seconds`（基准 3,600 秒） | `batch_validate` 按本批并发路数放大，只补偿本批自己引入的争用 |
| 一次决策的墙钟 | `budgets.strategy_inference_timeout_seconds`（基准 360 秒） | 超时与抛错一样，整个回放失败 |
| 策略容器 | 8 核 / 16 GiB，`/tmp` 与 `/dev/shm` 各 2 GiB（都算在这 16 GiB 里） | `--memory-swap` 与 `--memory` 同值：超了不是变慢，是直接 OOM 杀掉（退出码 137） |
| 显存 | 本臂 `gpu_count = 0` | 四条腿全是 CPU 上的 pandas / numpy，载体腿另有 LightGBM |

## 每条腿花什么

- **`n1` 与 `c_shuf`：不训练。** `fit` 直接返回；每次复核读一次 200 个自然日的日线面板（成分并集）、一次 640 个自然日的两张前十大股东表（按 `ts_code` 与 `ann_date` 下推），排序、出单。非复核日在确认最新可见交易日之后直接返回 `[]`。
- **`c_base` 与 `n2`：载体的季度重训。** 三年窗口的 158 个 Alpha158 算子加一个 LightGBM，续训、每第 4 次冷启动；同谱系在同一台宿主上实测单次十几到六十秒、容器峰值 2–3 GiB。第一研究年的 `fit` 更快，因为成分标签从 2020-01 才有，训练窗只有约一年半（`pit-field-map.md` 的数据下限）——那一年的秒数不能外推。
- **北向读取本身很便宜**：两张表在沪深 300 成分并集上 640 天约几万行。它只在复核日读，与 `fit` 无关。

## 本包要求的两件事

1. **整期批次之前，每条要进批次的腿各用 `smoke_backtest(start=研究期靠后的槽)` 跑一次**，读 `resources` 里的 `fit_seconds`、`peak_memory_bytes` 与逐日 `strategy` 秒数，写进结果笔记。
2. **同一个 `start` 复用。** `window_build_seconds` 是这个窗口一次性的开窗成本，付一次，后面同一个 `start` 的探针直接复用，永远不要乘以天数；整期批次从研究期开头开窗，根本不付这一笔。

单跑的秒数对宿主负载极敏感，耗时结论按多日回放的平均读，不按一次探针。
